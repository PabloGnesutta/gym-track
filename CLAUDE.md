# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Gym Track: a mobile-first PWA for logging gym exercises, sets, and reps. Vanilla JS frontend (no framework, no bundler, no build step) with a Node.js backend. The backend has real password-based accounts and a proper `/api/*` router (`backend/src/http/apiRouter.js`) backed by SQLite, matching the sibling car-track/fridge-track apps — see "Backend" and "Accounts" below. **Exercise/session data is now server-backed and account-scoped**: `local-db/exercise-db.js`/`set-db.js` call the API, not IndexedDB, so the same account sees the same data from any device/browser. IndexedDB is only still touched for a one-time legacy-data import on first login (see "Legacy data import" below) — it's not written to as part of normal use anymore.

This repo is one of several sibling "-track" apps (car-track, fridge-track) that share the same structure — car-track in particular was the direct model for this backend/accounts rewrite (same single-owner-per-row shape, unlike fridge-track's multi-user "Home" sharing model). Be careful not to cross-contaminate: this project's frontend content (index.html, app.js, ui.js) should stay gym-specific — do not copy in UI/markup from a sibling project. Also don't take a sibling's own CLAUDE.md as ground truth without checking the actual code first — car-track's, for one, was found stale (still describing a since-replaced local-only backend) partway through this rewrite.

**Requires Node ≥24** (`backend/package.json`'s `engines`) — the server-side schema is built on the built-in `node:sqlite` module.

**Allow-listed signup**: creating an account requires the email to already be in the `allowed_emails` table (same anti-abuse gate car-track/fridge-track use). Manage it via `node src/db/manageAllowedEmails.js add|remove|list <email>` from `backend/` — there's no UI for this. `pablo.gnesutta@gmail.com` is already allow-listed on the local dev database as of this writing.

## Commands

The repo has two independent npm projects (`backend/`, `frontend/`); there is no root-level package.json or build step.

**Backend (`backend/`)**:
```
npm run serve       # nodemon on src/index.gym-track.js, reads PORT from backend/.env (copy .env.example first)
npm test             # unit tests: node --test (backend/test/*.test.js)
node --test test/exerciseService.test.js   # run a single test file
npm run typecheck    # tsc --noEmit (backend/tsconfig.json)
```

**Frontend (`frontend/`)** — no bundler/build step; every file is loaded exactly as written by the browser (`<script type="module">`) or served as-is by the backend:
```
npm test                          # unit tests: node --test (frontend/test/*.test.js)
node --test test/date.test.js     # run a single unit test file
npm run typecheck                 # tsc --noEmit (frontend/tsconfig.json)
npm run test:e2e                  # Playwright e2e (frontend/e2e/*.spec.js)
npx playwright test e2e/session.spec.js    # run a single e2e spec
npx playwright test -g "some title"        # run e2e tests matching a title
```
`test:e2e` auto-starts and tears down the backend server itself, on its own port and its own sqlite file (`3999` / `backend/data/gymtrack.test.db`, set via `playwright.config.js`'s `webServer.env` — see `e2e/testPort.js`) — deliberately isolated from a manually-run `npm run serve` (port from `backend/.env`, `gymtrack.db`) so an e2e run can never collide with or wipe real local dev data. Don't start the backend manually before running e2e. `npx playwright install chromium` is a one-time setup step if the browser binary isn't already downloaded.

Both `typecheck` scripts run real `tsc --noEmit` against the existing JSDoc annotations (`tsconfig.json` in each project, `checkJs`/`allowJs`/`noEmit`, no `strict`) — unlike the sibling fridge-track/car-track projects, which only have editor-level (`.vscode/settings.json` `checkJs`) type checking with no scriptable CLI command. Keep annotating new code with JSDoc rather than converting files to `.ts`; the two `tsconfig.json`s are intentionally separate (frontend targets `lib: ["DOM"]` for browser globals, backend targets Node's `types: ["node"]`) since the two runtimes don't share globals.

## Architecture

### Frontend (`frontend/js/`)

Vanilla JS with ES modules (`type="module"`), no framework. Structure:
- `local-db/` — data access layer, one file per entity (`exercise-db.js`, `set-db.js`, `muscle-db.js`), despite the name **API-backed, not IndexedDB-backed**. Functions here call `api-caller/apiCaller.js`, convert the response shape (server fields → the client's existing `Exercise`/`Session` shape, e.g. `exerciseFromApi`/`sessionFromApi`), and mutate the in-memory `dbStore` cache — same exported function signatures as before this migration (`createExercise`, `updateExercise`, `deleteExercise`, `fetchExercises`, `createSet`, `getSessionsForExercise`, `deleteSession`), so `ui/*.js` didn't need to change shape, just what a couple of call sites do (see below). `muscle-db.js` is the one documented exception to the mutate-in-place convention — see "Conventions to preserve" below.
- `ui/` — DOM rendering and event wiring, one file per view/entity (`exercise-ui.js`, `set-ui.js`, `analytics-ui.js`, `muscle-ui.js`, `ui.js`). No component framework — elements are built with the `$new`/`$button` helpers in `lib/dom.js` and appended directly to fixed containers already present in `index.html`. `ui.js` also owns the header hamburger menu (`toggleHeaderMenu`/`closeHeaderMenu` — closes on any click outside `#headerMenu` or on any click inside the panel itself, since every item is a one-shot action; `refreshHeaderMenuEmail()` re-reads `getUserEmail()` on every open, not just once at boot, since logging out and back in never reloads the page) and the bottom tab bar (`#tabExercisesBtn`/`#tabAnalyticsBtn`, wired purely through `data-click-action`/`data-tab` like every other delegated click — no per-button listener; the active tab's color comes from a CSS attribute selector on `data-current-view`, not JS).
- `lib/dialog.js` — a reusable `showConfirm({title, message, confirmLabel?, cancelLabel?}) -> Promise<boolean>` / `showAlert({title, message, okLabel?}) -> Promise<void>` pair that replaced every native `confirm()`/`alert()` call in the app. Lives in `lib/`, not `ui/`, specifically because `local-db/legacyImport.js` needs to call it and the documented data-flow (`ui/*.js` → `local-db/*.js`) forbids `local-db` importing from `ui`; `lib/logger.js` is the existing precedent for a DOM-touching module importable from both layers. Wires its listeners against the static `#dialogOverlay` markup in `index.html` at plain module-top-level (same pattern `logger.js` uses for `#closeLogsBtn`), so it's ready before `app.js`'s synchronous `initUi()`/`initAuthUi()` calls, let alone the later async `afterLogin()` → `maybeImportLegacyData()` chain, ever run. e2e tests now interact with `#dialogOverlay`'s real DOM (`#dialogConfirmBtn`/`#dialogCancelBtn`) instead of Playwright's `page.on('dialog', ...)`.
- `common/state.js` — three global, mutated-in-place state objects: `appState` (UI flags like `showExerciseForm`, also mirrored onto `$app.dataset` for CSS state-driven styling), `dataState` (currently-open exercise/session), and `dbStore` (in-memory cache of the current account's exercises/sessions, populated from API responses — exercises array, sessions keyed by exercise key as strings).
- `lib/indexedDb.js` — thin generic wrapper around the IndexedDB API (`putOne`, `getOne`, `getAll`, `getOneWithIndex`, `getAllWithIndex`, `deleteOne`, `deleteMany`). No longer used for exercises/sessions day-to-day — its only remaining caller is `local-db/legacyImport.js`'s one-time read (see below). `whenDbReady()` gates any DB access before initialization completes.
- `lib/utils.js` — includes a tiny pub/sub `eventBus`. The only current event is `IndexedDbInited`, emitted once the DB opens; `app.js` waits on it before calling `bootApp()`.
- `api-caller/apiCaller.js` — wraps `fetch` to the backend's `/api/*` routes with the bearer session token from `localStorage`, always POSTs, always resolves `{data}`/`{error}` (never throws). `apiSignup`/`apiLogin`/`apiLogout` back the boot/auth flow; `apiCreateExercise`/`apiFetchExercises`/`apiUpdateExercise`/`apiDeleteExercise`/`apiFetchSessions`/`apiAddSet`/`apiUpdateSession`/`apiDeleteSession` are what `local-db/exercise-db.js`/`set-db.js` call internally.
- `appBoot.js` — `bootApp(initialRoute)` (called from `app.js`'s `IndexedDbInited` handler, passed the route captured before boot - see "Navigation & routing" below): checks `isLoggedIn()` and stops at the login screen (`appState.authStage = 'login'`) if there's no cached session, otherwise calls `afterLogin()`. `afterLogin()` sets `authStage = 'ready'`, offers the one-time `maybeImportLegacyData()` (see below), fetches exercises, then applies the captured initial route (deep link/refresh) if there was one, falling back to `openExerciseList()` otherwise. `logout()` calls the API to invalidate the session token, clears `dataState.currentExercise`/`currentSession` (the `dbStore` caches and rendered list are cleared by `fetchAndRenderExercises()` itself on the next login, not here — see its own doc comment for why that's the more robust place), then drops back to the login screen.
- `ui/auth-ui.js` — wires the login/signup form (`#authForm`, toggled between modes via `#authModeToggle`) and calls `afterLogin()` on success. The header menu's logout item itself is wired in `ui.js` (where every other header/view button is, per that file's own centralizing convention), which calls back into `auth-ui.js`'s `resetAuthMode()` so a fresh logout always lands on the login form rather than wherever signup/login mode was left.
- `ui/analytics-ui.js` — `openAnalytics()` and the three widget renderers backing the Analytics tab — see "Analytics" below for the full design.

**Data flow for a typical action** (e.g. adding a set): UI event handler in `ui/*.js` → local-db function in `local-db/*.js` (validates, calls the API via `apiCaller.js`) → local-db function updates `dbStore`/the mutated object in place → UI function re-renders the affected DOM node directly (no reactive re-render; each mutation manually patches the relevant element).

**Auth gates the DOM the same way view-switching does**: `#app`'s `data-auth-stage` attribute (`'checking'` → `'login'` or `'ready'`, via `setAuthStage()` in `state.js`) drives `css/auth.css`'s `#app:not([data-auth-stage='ready']) #mainHeader, .views { display: none }` / `#app[data-auth-stage='login'] #authView { display: flex }` rules — the same CSS-attribute-selector pattern `currentView`/`showExerciseForm` already use, not a JS show/hide toggle.

**`fetchAndRenderExercises()` (`exercise-ui.js`) is deliberately idempotent** — it clears the rendered `.list` DOM and the `dbStore.exercises`/`dbStore.sessions` caches before repopulating, rather than assuming it only ever runs once per page load. That assumption held before accounts existed (no way to trigger a second boot cycle without a full page reload, which naturally reset everything); now that `logout()` → `login` can happen within the same page load, skipping this would duplicate every row on screen and in `dbStore` (a real bug an e2e test caught during this migration) and could leak a stale `dbStore.sessions` entry from one account into another's view, since exercise ids restart from 1 per account.

**IndexedDB schema** (`frontend/js/lib/indexedDb.js`, only relevant to the legacy-import path now): database `GymTrack`, two stores, `exercises` (autoIncrement key, unique index on `name`) and `sessions` (autoIncrement key, non-unique index on `exerciseKey`) — same shape the server schema mirrors. Because `dbVersion` bumps trigger `onDbOpenError` with `VersionError` handling that **deletes and recreates the whole database**, never lower `dbVersion` against a codebase with local data you want to keep.

### Legacy data import (`frontend/js/local-db/legacyImport.js`, `importBatch.js`)

One-time upgrade path for anyone using the app from before accounts existed: `maybeImportLegacyData()` (called from `appBoot.js`'s `afterLogin()`) reads a small JSON status object from the `legacyImportStatus` `localStorage` key (`{status: 'declined'|'complete'|'pending'}` — a bare `true`/`false` flag isn't enough, see below). If unset, it reads whatever's still in this device's IndexedDB (`getAll('exercises')`), and if there's anything, asks (native `confirm()`) whether to upload it to the now-logged-in account; declining sets `'declined'` and never asks again. `importBatch.js`'s `importBatch({exercises, sessions})` does the actual upload, in dependency order: each exercise via `exercises/create` (reusing the id of one that already exists by name instead of re-creating it - see below), then each session — recreated via one `sessions/addSet` call (using its first weight row's first rep, just to create it on the right calendar day) followed by one `sessions/update` call overwriting it with the session's *exact* original `sets`/`notes`, since the backend has no bulk "create session with these exact sets" endpoint and replaying rep-by-rep through `addSet`'s own same-day/same-weight grouping logic wouldn't reliably reproduce an already-grouped session.

**Deliberately idempotent, and only marked `'complete'` when nothing failed.** A real user hit silent, large-scale data loss here: `apiCall()` (`apiCaller.js`) never throws - a rejected request (a dropped mobile connection, or a reverse-proxy rate limit; both are realistic for a long unthrottled sequence of requests uploading months of history) just resolves to `{error}`, and the old version of this code both kept going past any per-item failure *and* unconditionally marked the whole import `'complete'` regardless, so a badly-interrupted run silently lost most of the data with no error, no retry, and no way to tell anything was wrong. Fixed by: (1) `importBatch()` fetches what the account already has first (`apiFetchExercises`/`apiFetchSessions`) and only creates what's missing - by exercise name, by session's calendar day - so it can be safely re-run; (2) it paces every write (~8/s) and retries once with backoff specifically on a 429/503; (3) `legacyImportStatus` only becomes `'complete'` when the run reported zero failures - a partial run is left as `'pending'`, which the next login retries automatically (no re-prompt, since the user already said yes once) instead of silently losing the rest; (4) either way, an `alert()` now reports what happened. The status key itself was renamed from an old plain `legacyImportDone` boolean specifically so a device already wrongly marked "done" under the pre-fix logic gets one more chance under the new one, with no manual `localStorage` surgery needed. Ported from car-track's `legacyImport.js`/`importBatch.js`, which solved the original (non-idempotent) version of this same problem for its own local-first → server-backed migration.

### Navigation & routing (`frontend/js/common/routeMatch.js`, `router.js`)

Real client-side URL routing, added so refreshing on an exercise doesn't reset to the list. Same split as fridge-track's own router: `routeMatch.js`'s `parseRoute(pathname)` is a pure, dependency-free `pathname -> Route` mapper (`{view: 'ExerciseList'}` / `{view: 'SingleExercise', exerciseKey}` / `{view: 'Analytics'}` / `{view: 'Muscles'}`), unit-tested directly (`frontend/test/routeMatch.test.js`); `router.js` wires it to `history.pushState`/`popstate` and the actual view functions. `syncUrl(path, {replace?})` is called *from* the view-opening functions themselves (`openExerciseList` replaces, since bouncing back to the list shouldn't pile up history entries; `openSingleExercise`/`openAnalytics`/`openMuscles` push), so every way of reaching a view - a click, a deep link, the browser's own back/forward - keeps the URL in sync automatically. `openSingleExercise` falls back to `openExerciseList()` when the URL's exercise id doesn't resolve (deleted, mistyped, another account's id) instead of leaving a blank view.

**Boot order matters, same reason as fridge-track**: `app.js` calls `captureInitialRoute()` *before* `initializeIndexedDb()`/`bootApp()` run, since `afterLogin()`'s default `openExerciseList()` call would otherwise reset the URL to `/` before a deep link ever gets a chance to render. The captured route is threaded through as a plain argument (`bootApp(initialRoute)` → stored as `appBoot.js` module state `pendingInitialRoute`) and applied exactly once, on the first `afterLogin()` resolution after exercises are loaded (so `openSingleExercise` can actually find the exercise) — a later logout/login within the same page load must *not* replay a stale route, so it's cleared to `null` right after being applied.

**`common/router.js` importing `openExerciseList`/`openSingleExercise` from `ui/exercise-ui.js`, which imports `syncUrl` back from `router.js`, is a deliberate circular import** — safe only because neither module touches the other's export at module top level, just inside function bodies invoked later (the same pattern fridge-track's own `appBoot.js`/`home-ui.js` circular import documents). Worth knowing about before "fixing" it.

**Because client-side routes exist now, every static asset reference must be root-relative** (`/js/app.js`, `/css/style.css`, `/static/manifest.json`, and the service worker registration call `navigator.serviceWorker.register('/cacheServiceWorker.js')` in `initializeCache.js`) — a relative path resolves incorrectly from a nested URL like `/exercise/42`. `backend/src/http/requestHandler.js` also gained an SPA fallback: any request whose last path segment has no `.` in it (not a static asset, not `/api/*`) serves `index.html` and lets the frontend router resolve the URL - without this, a hard refresh on `/exercise/42` would just 404 server-side before the client-side router ever got a chance to run.

### Design system (`frontend/css/`)

Dark theme driven entirely by CSS custom properties defined once in `style.css`'s `:root` — every other CSS file (and every per-form/per-view override) references these tokens rather than hardcoding colors. Before this pass the palette was an unplanned mix of purple/crimson/dark-red/dark-green/navy/magenta/cyan picked ad hoc per component; it's now:
- `--surface-0` … `--surface-4` — a violet-slate neutral scale (darkest → lightest), used for page/header/card/input backgrounds and borders. List rows use `--surface-2` as their baseline (previously every row was a loud solid purple regardless of state) - color is now reserved for actual emphasis, not the default.
- `--text-primary`/`--text-secondary`/`--text-muted`/`--text-faint` — the only text colors used anywhere.
- `--accent`/`--accent-strong`/`--accent-soft` — one violet accent for every primary action (FAB, every form's submit button, focus rings, links). All four forms' submit buttons (`exerciseForm`/`createSetForm`/`sessionForm`/`authForm`) share one selector for this in `input.css`, instead of three near-duplicate declarations each in a different random color.
- `--status-today`/`--status-today-text`/`--status-today-bg` — the one semantic status color, for "a set was logged today" (the current-date session log, and a left-border accent + green timestamp on that exercise's list row).
- `--form-exercise-*` (violet) / `--form-set-*` (teal) / `--form-session-*` (rose) — harmonized jewel-tone pairs (same saturation/lightness family, so they read as siblings, not clashing) giving each of the three data-entry forms a distinct identity while every other property (buttons, inputs, spacing) stays shared. This exact "harmonized jewel tones, same lightness family" approach, and the `--overlay-*`/`--press-bg`/`--scrim`/`--shadow`/`--log-*` utility tokens, are ported from car-track's own design-token system - not copied wholesale (gym-track's accent is violet, not car-track's blue, and the surface scale is tinted toward it), but same structure, for the same reason: keeps new UI additions from reintroducing one-off colors.
- `color-scheme: dark` on `:root` (also ported from fridge-track) so native form-control chrome (scrollbars, autofill, etc.) follows the theme instead of defaulting to a light system theme.

When adding new UI, reach for an existing token before writing a new hex value; if a new form/section genuinely needs its own identity, add a new `--form-*` pair at the same saturation/lightness as the existing three rather than a one-off color.

### PWA / caching (`frontend/cacheServiceWorker.js`)

Static-asset caching via a service worker with a versioned cache name (`MAJOR_VERSION`). `INTERCEPT_FETCH_REQUESTS` toggles whether the service worker intercepts fetches at all:
- Set to `false` during local development so hot-reloaded changes are visible immediately (otherwise the cached version is always served).
- Set to `true`, and bump `MAJOR_VERSION`, before shipping a release.

See [frontend/js/README.md](frontend/js/README.md) for the same note in context.

### Backend (`backend/src/`)

Plain Node.js `http` server (no Express/framework), ESM (`"type": "module"`), following the exact structure of car-track's/fridge-track's own backends.
- [index.gym-track.js](backend/src/index.gym-track.js) — entry point; loads `.env`, imports `db.js` (runs pending migrations as a side effect), starts `createServer(handleRequest)`.
- [http/requestHandler.js](backend/src/http/requestHandler.js) — serves `frontend/` static files by path prefix (`css/`, `js/`, `static/`, `/`→`index.html`), merges [http/securityHeaders.js](backend/src/http/securityHeaders.js)'s `SECURITY_HEADERS` (strict CSP — the app has zero inline scripts/styles/third-party resources, so this costs nothing) into every response, and delegates anything under `/api` to `apiRouter.js`'s `handleApiRequest`. Also has an SPA fallback for client-side routes (any path whose last segment has no `.` in it serves `index.html`) — see "Navigation & routing" below.
- [http/apiRouter.js](backend/src/http/apiRouter.js) — `handleApiRequest(req, res, segments)`: joins the path segments after `api/` into a route string and dispatches via an `if` chain (not a bare `switch` on `req.url` like before — this is the "actual router" work). All routes are POST-only, matching `apiCaller.js`. `signup`/`login` are public; everything else requires a valid `Authorization: Bearer <token>` resolved via `getBearerUser()`. A `ServiceError` thrown by any service maps to a 400; anything else unexpected is logged and mapped to a 500. Add new routes here, following the existing `if (route === '...') { return successResponse(res, someService.doThing(user.id, ...)); }` shape.
- [http/bodyParser.js](backend/src/http/bodyParser.js) — `readJsonBody(req)`, used directly by `apiRouter.js` (no separate content-type switch in `requestHandler.js` anymore).
- [http/httpResponses.js](backend/src/http/httpResponses.js) — `successResponse(res, data)` / `errorResponse(res, msg, status)`, both merging `SECURITY_HEADERS`.
- [auth/passwordHash.js](backend/src/auth/passwordHash.js) — `hashPassword`/`verifyPassword` via `node:crypto`'s `scryptSync` + `timingSafeEqual`. No JWT anymore (the old `auth/jwt.js`/`controllers/auth-controller.js`/`http/middleware.js` were removed) — sessions are opaque random tokens stored server-side (see below), not self-contained signed tokens, so there's no `TOKEN_SECRET` to protect or leak.

### Accounts (`backend/src/services/authService.js`, `backend/src/db/allowedEmails.js`)

Real password-based accounts, replacing the old anonymous-visitor JWT entirely:
- `createUser(email, password, name?)` requires the email to be in `allowed_emails` first (`isEmailAllowed`) — signup is invite-gated, not open. Manage the list via `node src/db/manageAllowedEmails.js add|remove|list <email>` (no UI).
- `verifyLogin(email, password)` checks the stored `scrypt` hash.
- `createSession(userId)` issues a random 32-byte hex bearer token, stored in the `auth_sessions` table (see schema below); `getUserBySessionToken(token)`/`deleteSession(token)` resolve/revoke it. `apiRouter.js`'s `getBearerUser()` is the only place that reads the `Authorization` header.
- Frontend: `js/api-caller/apiCaller.js`'s `apiSignup`/`apiLogin`/`apiLogout` persist/clear `accessToken`/`userId`/`userEmail`/`userName` in `localStorage`; `isLoggedIn()` is just `!!accessToken`. `js/appBoot.js` + `js/ui/auth-ui.js` wire this into the boot flow and the `#authView` login/signup form — see the Frontend section above.

**What accounts do**: logging in gates *access* to the app (`authStage`) *and* scopes exercise/session data — every route is scoped by `user_id` server-side (see below), so two accounts on the same device (or the same account from two different devices) each see only their own exercises/sessions. There's still no cross-account sharing of any kind (no "Home"/team concept like fridge-track) and no offline support (every read/write is a live API call — see "Still not done" below).

**Still not done**: no offline/local-cache fallback (fridge-track's sync engine, with its own outbox/LWW-merge machinery, is the model to follow if this app ever needs it — nothing here attempts that yet, every `local-db/*.js` call just fails outright if the network is down); no password reset; no account deletion; no rate-limiting on login attempts.

### Server-side database (`backend/src/db/`)

`node:sqlite`-based, mirroring car-track's/fridge-track's own setup:
- [db/db.js](backend/src/db/db.js) — opens `backend/data/<DB_NAME>.db` (a `node:sqlite` `DatabaseSync`, gitignored; `DB_NAME` env var defaults to `gymtrack.db`, overridden to `gymtrack.test.db` for e2e — see "Commands" above) and runs pending migrations. WAL journal mode + a 5s busy timeout, so concurrent readers/writers (e.g. e2e test helpers opening their own short-lived connection to the same file) don't collide.
- [db/migrate.js](backend/src/db/migrate.js) — generic migration runner: each migration runs at most once, tracked in a `schema_migrations` table, inside its own transaction. A migration is `{version, name, sql?, migrate?}` — `sql` is a plain string exec'd as-is; `migrate` is a `(db) => void` function for migrations that need real JS-side data transformation during backfill (e.g. locale-aware string normalization SQLite itself can't do — see `003_muscles` below). A migration can supply either or both; both run inside the same per-migration transaction.
- [db/migrations/](backend/src/db/migrations) — `NNN_description.js` files exporting a `sql` string and/or a `migrate` function, registered in order in `migrations/index.js` (an explicit array, not directory-scanning). **Never edit an already-shipped migration** — add a new migration with the next version number instead.
  - `001_initial_schema` — original `exercises`/`sessions` tables (no accounts yet at that point).
  - `002_accounts` — adds `users`, `auth_sessions` (named `auth_sessions`, not `sessions`, specifically to avoid colliding with the pre-existing workout-session table), and `allowed_emails`; **drops and recreates** `exercises`/`sessions` with a `user_id` column (`exercises.name`'s unique constraint also widened from global to per-`(user_id, name)`, so two accounts can each have their own "Sentadilla") — safe as a plain drop specifically because no route ever existed to write to either table before this migration shipped. A future recreate-table migration against a table that *does* have real rows must copy them across instead (rename-aside + `INSERT ... SELECT`, per fridge-track's own `008_locations_category_id.js`).
  - `003_muscles` — moves exercise muscle tags off a comma-joined `exercises.muscles` string column into a real many-to-many relationship: `muscles` (one row per user per canonical muscle name, `UNIQUE(user_id, name)`) + `exercise_muscles` join table. Written as a `migrate` function specifically because the backfill needs Spanish-aware lowercasing (`trim().toLocaleLowerCase()`) — **SQLite's own `LOWER()` is ASCII-only** (empirically confirmed: `SELECT LOWER('TRÍCEPS')` → `'trÍceps'`, the accented `Í` untouched), so normalization has to happen in JS, never in raw SQL. Finishes with `ALTER TABLE exercises DROP COLUMN muscles` — a plain `DROP COLUMN`, not a rename-aside + recreate, since this box's bundled SQLite (3.53.3) supports it natively (added in 3.35). `muscles.name` *is* the canonical (trimmed, lowercased) form — there's no separate display name; the UI applies `text-transform: capitalize` for display instead of trusting stored casing.
- [services/exerciseService.js](backend/src/services/exerciseService.js) / [services/sessionService.js](backend/src/services/sessionService.js) — `create*Service(db)` factories, every function scoped by `userId` (mirrors car-track's `vehicleService.js`'s `getOwnedVehicleRow` ownership-check pattern via `getOwnedExerciseRow`). `sessionService` takes an injected `exerciseService` (defaulting to a real one) purely to reuse its ownership check rather than duplicating that query — same cross-service-reuse shape as fridge-track's `syncService` reusing `homeService`'s `assertHomeMembership`. `exerciseService.listExercises` joins in each exercise's most recent session via a correlated subquery (aliased `ls_*` columns) and its muscle tags via a `GROUP_CONCAT` subquery, so the client's list view gets both in one round trip instead of N+1 — mirrors what the old IndexedDB-denormalized `exercise.lastSession` gave the client for free. `linkMuscles(userId, exerciseId, muscles)` is the shared normalize-dedupe-upsert-link helper both `createExercise` and `updateExercise` build on (`normalizeMuscle` = `trim().toLocaleLowerCase()`, same rule the `003_muscles` backfill uses); `updateExercise` only touches muscle tags when `patch.muscles !== undefined`, and does a full delete-then-relink to match the old comma-string's overwrite semantics — it deliberately leaves now-orphaned `muscles` rows in place (cheap, and lets a future tag-autocomplete or a re-added tag reuse the canonical row instead of recreating it). `addSet` (`sessionService.js`) also bumps its parent exercise's `updated_at` to the set's own date (not necessarily "now") — ported directly from the pre-migration client's own `createSet`, which did the same via a `updateExercise(exercise, null, null, date)` call, so the exercise list's "most recently used first" sort keeps working now that the timestamp lives server-side. [services/ServiceError.js](backend/src/services/ServiceError.js) is a plain `Error` subclass the router maps to a 400.
- [services/muscleService.js](backend/src/services/muscleService.js) — `createMuscleService(db)` factory backing the Muscles management view (see below), following the same `getOwnedMuscleRow(userId, muscleId)` ownership-guard shape as `exerciseService.js`'s `getOwnedExerciseRow`.
- [test/](backend/test) covers all of the above (including `authService.test.js` and multi-user data-isolation cases) against an in-memory (`:memory:`) database.

**Routes** (all POST, bearer-gated except signup/login): `signup`, `login`, `whoami`, `logout`, `exercises/fetch`, `exercises/create`, `exercises/update`, `exercises/delete`, `muscles/fetch`, `muscles/rename`, `muscles/delete`, `sessions/fetch`, `sessions/addSet`, `sessions/update`, `sessions/delete`, `analytics/summary`.

### Analytics (`backend/src/services/analyticsService.js`, `frontend/js/ui/analytics-ui.js`)

The `#analyticsView` tab (muscle-group balance, weekly training frequency, personal records) is computed **fresh server-side on every visit, not cached client-side** — a deliberate call, not the default. The tempting alternative (cache sessions in IndexedDB with a "last fetched" marker, sum on the client) was rejected: every mutation (`addSet`/`updateSession`/`deleteSession`/`deleteExercise`) would need to correctly invalidate that cache or the page could silently show stale numbers, and this app has no offline story anywhere else to justify carrying that complexity for one page — see "Still not done" above. At personal-app data volumes (a few hundred sessions at most) the aggregation queries below cost nothing worth caching.

`createAnalyticsService(db)` exposes three independently-callable, independently-tested functions plus a `getSummary(userId)` that combines them into the one payload `analytics/summary` returns (one request covers all three widgets, since the page always needs all three at once):
- `getMuscleBalance(userId, days=30)` — sets per muscle tag over the trailing window, most-worked first. Muscles join in via a normal SQL join (`sessions` → `exercise_muscles` → `muscles`, see `003_muscles` above) since they're a real relationship now, not string-parsing; `muscles.name` is already the canonical normalized form so no normalization is needed on the read side. `sets` itself is still a JSON blob though, so the actual per-set counting stays in JS (unpacking it in raw SQL via `json_each` would buy nothing at this data volume). "Sets" here means every element of every weight row's `r` array (`{w: 40, r: [10, 8]}` is 2 sets), matching how `set-ui.js` already renders it ("40kg X 10,8") - not the number of distinct weights logged.
- `getTrainingFrequency(userId, weeks=8)` — distinct **calendar days** trained per week bucket (local time, same day semantics as `sessionService.js`'s own `isSameDay`), oldest to newest. Counts days, not sessions — two different exercises trained the same day is one day of consistency, not two.
- `getPersonalRecords(userId)` — per exercise, heaviest single set ever and best estimated one-rep max (Epley: `weight × (1 + reps/30)`) across every individual set, sorted by whichever PR was set most recently (reads like a small achievement feed, not an arbitrary leaderboard).

Frontend: `analytics-ui.js`'s `openAnalytics()` fetches the summary and hands each piece to its own render function, all three built the same way as everywhere else in this app - `$new()` elements appended directly, no framework. Bar widths/heights are the one thing `$new()` can't express (no `style` param), so those are set via a plain `element.style.width/height = ...` right after creation.

### Muscles view (`backend/src/services/muscleService.js`, `frontend/js/ui/muscle-ui.js`)

Reachable via the header hamburger menu ("Músculos", `#musclesMenuBtn`). Lists every muscle tag the account has, each with how many exercises currently reference it (`listMuscles`, a `LEFT JOIN exercise_muscles` + `COUNT` grouped query), with inline rename and delete per row.

- **Rename merges on collision.** `renameMuscle(userId, muscleId, newName)` normalizes `newName` the same way `exerciseService.js` does; if another muscle the user already has shares that normalized name, it **merges** rather than rejecting as a duplicate — every exercise linked to the old muscle is relinked to the existing target (`INSERT OR IGNORE INTO exercise_muscles ... SELECT exercise_id, <targetId> FROM exercise_muscles WHERE muscle_id = <oldId>`, the `OR IGNORE` silently no-ops for an exercise that already carried both tags), the old links are dropped, and the now-empty old `muscles` row is deleted. A plain rename (no collision) is just an `UPDATE`. Either way the surviving row's id+count is returned, so the caller doesn't need to know which branch ran.
- **Delete cascades.** `deleteMuscle` drops every `exercise_muscles` link for that muscle, then the `muscles` row itself — every exercise that had it tagged simply loses the tag. The frontend warns with the affected exercise count before calling this (via the reusable dialog, see below) rather than deleting silently.
- Since a muscle is a real FK reference (not a copy of a name on each exercise, see `003_muscles`), rename/merge/delete are immediately reflected everywhere that muscle is used — `muscle-ui.js` calls `fetchAndRenderExercises()` (from `exercise-ui.js`) after a rename or a delete-of-a-used-tag specifically because `dbStore.exercises`/the rendered exercise list are populated once at boot and never otherwise invalidated (see that function's own doc comment) — without this refresh, the exercise list's search-by-muscle and the single-exercise view would keep showing the tag under its old name until the next login.
- No client-side cache (`local-db/muscle-db.js` has no `dbStore.muscles` equivalent) — same "always fresh, no invalidation to get wrong" call Analytics makes above.

## Conventions to preserve

- JSDoc types (`@typedef`, `@param`, `@returns`) are used consistently in place of TypeScript; keep annotating new functions the same way rather than converting the project to `.ts`.
- Store mutation functions (`local-db/*.js`) mutate the passed-in object (e.g. `updateExercise` mutates the `exercise` argument) rather than returning a new one — callers rely on this to update `dbStore` in place without a separate replace step. **`local-db/muscle-db.js` is the one documented exception** — it returns fresh data instead, since there's no `dbStore.muscles` cache anything holds a long-lived reference to (the Muscles view always re-fetches).
- Every native `confirm()`/`alert()` in the app has been replaced by `lib/dialog.js`'s `showConfirm()`/`showAlert()` (see "Muscles view" above for why — a count-aware cascade-delete warning native `confirm()` can't express) — don't reach for the native browser dialogs in new code, use these instead.
- Some UI copy is in Spanish (form labels, confirm dialogs, error messages like `'Ingresar nombre'`); match the existing language per string rather than switching wholesale.
- **Frontend unit tests only cover DOM-free modules.** `js/lib/dom.js` and `js/lib/logger.js` touch `document`/`window` at module top level, so importing anything that transitively pulls them in (most of `ui/*.js`, `local-db/*.js`, and `common/router.js` since it imports from `ui/*.js`) crashes under plain `node --test`. `frontend/test/` therefore only targets modules with no such dependency (`lib/date.js`, `lib/string.js`, `common/routeMatch.js` today) — same constraint fridge-track's own frontend test suite documents, and the same reason `routeMatch.js` is split out from `router.js` in the first place. UI-level behavior belongs in the Playwright e2e suite instead, where every test gets a fresh browser context (empty IndexedDB) for free.
- **Every e2e test needs a logged-in session first** (the app now gates behind login) — call `ensureAuth(page)` from `e2e/helpers.js` at the top of the test/`beforeEach` (it allow-lists a freshly-generated unique email against the e2e backend's own sqlite file, then signs up). `e2e/auth.spec.js`/`e2e/legacyImport.spec.js` deliberately do their own signup/login by hand instead, since they're testing that flow directly. `e2e/helpers.js`'s `logOut(page)` opens the header hamburger menu and clicks "Cerrar sesión" for you — the logout button lives inside that (initially hidden) panel now, not as a standalone header icon.
- **Opening a second IndexedDB connection from an e2e test must omit the version argument.** `e2e/legacyImport.spec.js`'s `seedLegacyExercise()` writes directly into the browser's IndexedDB (bypassing the app, to simulate a pre-accounts install) via its own `indexedDB.open('GymTrack')` call. Pinning that to the app's own `dbVersion` (`indexedDb.js`'s `102`) reliably fires `blocked` instead of `success` while the app's own connection is still open, hanging the test until Playwright's timeout — even though same-version opens aren't supposed to block per spec. Opening with no version argument (just "whatever's already there") sidesteps it entirely.
